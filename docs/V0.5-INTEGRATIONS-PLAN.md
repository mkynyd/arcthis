# v0.5+ integrations plan

Status: Stage 1 / v0.5 complete; Stages 2–6 planned

This document splits the broad integration roadmap into six capability-gated stages. Version labels are provisional; a stage ships only when its contracts, limits, security review, tests, and documentation agree. Stage 1 shipped in v0.5; later commands and interfaces remain unimplemented unless the roadmap explicitly marks them complete.

## Goals

- Make the existing archive access library usable by agent runtimes without shell-text parsing.
- Preserve the same format-independent access semantics across CLI, MCP, remote locators, services, and bindings.
- Keep archive decoding synchronous and streaming in the core unless measured frontend or remote-source requirements justify an async adapter.
- Keep destructive operations plan-first, bounded, auditable, and disabled unless a frontend has an explicit filesystem policy.
- Avoid sending unbounded entry bytes into model context or materializing entire remote archives by default.

## Non-goals shared by all stages

- Reimplementing codecs, media renderers, object-store clients, SSH, or FUSE protocols.
- Treating MCP filesystem roots as an authorization boundary.
- Exposing arbitrary host filesystem access from a server with default settings.
- Promising efficient random access when the archive format or remote origin cannot provide it.
- Making mount, TUI, or preview behavior part of the core archive abstraction.

## Stage 1 — v0.5: integration foundation and local MCP

Stage 1 was delivered as three sequentially verified vertical slices.

### 1A. Frontend-neutral application service

- Add typed request/result models above `Archive` for inspect, list, tree, stat, read, find, grep, hash, and verify.
- Reuse the existing public error categories and schema version without coupling the service to Clap or terminal output.
- Define cancellation checkpoints, decoded-byte budgets, result-count limits, and bounded read windows.
- Write an RFC for MCP tool names, resource URI grammar, path policy, protocol-version support, and binary content transport before changing public CLI grammar.

Exit gate: the CLI can call the service layer without observable schema or byte-stream regressions, and library tests exercise the same operations without spawning the CLI.

Completion: passed direct service tests, unchanged CLI schema/raw-byte regressions, and real read/verify smoke tests across every supplied archive family.

### 1B. Read-only stdio MCP server

- Prefer a feature-gated `arcthis mcp` frontend so the default product remains one installable binary; the RFC may choose a separate binary only with a measured packaging reason.
- Expose read-only structured tools for inspect/list/tree/stat/find/grep/hash/verify.
- Expose entry content through bounded text/blob reads or resource links. Large reads require offset/length windows or an external streaming handoff; no tool returns an unbounded base64 payload.
- Use declared input and output JSON Schemas and mirror structured results into compatible text content when required by negotiated MCP revisions.
- Reserve stdout exclusively for MCP messages and send diagnostics to stderr.
- Configure allowed local roots explicitly through server configuration or launch arguments. MCP roots are informational and must not be treated as access control.
- Mark tools with truthful read-only/idempotence annotations, while treating annotations as hints rather than security enforcement.

Exit gate: official protocol conformance for the pinned revision, subprocess stdio tests with at least two independent MCP clients/inspectors, malformed-message tests, zero stdout contamination, bounded content tests, cancellation tests, and macOS/Linux CI.

Completion: passed official MCP Inspector strict discovery/tool calls and an independent raw JSON-RPC subprocess harness covering schema discovery, malformed input recovery, stdout purity, root denial, bounded reads, and cancellation. The macOS/Linux workflow runs all-feature Clippy, tests, and release builds.

### 1C. Controlled mutation tools

- Add extract, pack, and convert only after read-only MCP is stable.
- Require an explicit output-root allowlist and reuse the core path sanitizer, collision policy, resource limits, staging, verification, and source/destination separation.
- Use a two-step plan/execute contract. Execution must echo a plan digest bound to source fingerprint, destination, limits, and collision policy so stale plans are rejected.
- Keep `--delete-source` equivalent disabled by default; enabling it requires an explicit server policy and a separately visible destructive tool contract.
- Accept password references only through configured secret providers or protected files, never ordinary tool arguments or results.

Exit gate: adversarial path tests, stale-plan rejection, destination race tests, cancellation at each lifecycle boundary, source preservation tests, and audit-safe structured errors.

Completion: passed extract/pack/convert plan and execute tests, non-mutating plan checks, source/destination fingerprint races, input/output symlink escapes, output-root denial, pre-perform cancellation, source preservation, verified deletion, and double-opt-in deletion policy.

## Stage 2 — v0.6: HTTP remote archive locator

- Write an `ArchiveLocator` RFC with an explicit URI/source model; do not reinterpret diagnostic `::` strings or filesystem paths.
- Implement a bounded HTTP source with redirects, timeouts, retry policy, maximum object size, cache policy, and SSRF protections.
- Use byte ranges only after validating status, `Content-Range`, object length, and a strong validator. Use `If-Range`/ETag semantics to prevent blocks from different object versions being combined.
- When ranges are unavailable, either stream sequential formats or download once into a bounded verified cache. Report the actual access strategy and cost warning through capabilities.
- Keep credentials out of URLs, JSON results, cache keys, and logs.

Exit gate: local origin matrix covering correct/ignored/malformed ranges, validator changes, redirects, interrupted transfers, cache invalidation, maximum-size enforcement, and request-count assertions for ZIP versus streamed TAR.GZ.

## Stage 3 — v0.7: authenticated S3 and SSH locators

- Add providers independently behind the Stage 2 source contract; do not route S3 or SSH through ad hoc shell commands.
- Use mature provider libraries for signing, credentials, host-key verification, proxy behavior, and ranged reads.
- Define credential precedence, profile selection, endpoint allowlists, S3-compatible endpoint behavior, SSH known-hosts policy, and redaction before implementation.
- Preserve provider-specific cost and seek capabilities without leaking SDK types into the archive API.

Exit gate: emulator/integration tests, expired/rotated credential tests, S3 version-change tests, SSH host-key mismatch tests, bounded retry tests, and no-secret logging snapshots.

## Stage 4 — v0.8: network service API

- Build a versioned HTTP API over the same application service, not over CLI subprocesses.
- Add authentication, per-principal filesystem/remote-source policy, request and decoded-byte quotas, rate limits, cancellation, observability, and streaming responses.
- Introduce Tokio only in this frontend if load and cancellation measurements justify it; the archive core remains synchronous.
- Publish an OpenAPI contract distinct from CLI JSON schema while sharing domain result types where semantics match.
- Start with stateless read operations. Mutation endpoints remain opt-in and retain the Stage 1C plan/execute contract.

Exit gate: authorization matrix, tenant isolation, quota and cancellation tests, slow-client/backpressure tests, structured error compatibility, and a documented deployment threat model.

## Stage 5 — v0.9: FFI and language bindings

- Start with a small C ABI using opaque handles, caller-owned buffers/writers, explicit cancellation, and stable error codes.
- Add a Python binding only when a real consumer exists; wrap the C ABI or a thin Rust facade rather than duplicating archive semantics.
- Keep streaming callbacks bounded and define thread-safety, handle lifetime, panic containment, and schema/version negotiation.
- Do not expose backend crate types, Rust lifetimes, or raw pointers without documented ownership rules.

Exit gate: ABI compatibility test fixture, sanitizer-enabled native tests, Python wheel tests on supported platforms if applicable, streaming of multi-gigabyte synthetic entries without whole-entry allocation, and binding-specific documentation.

## Stage 6 — post-v0.9: human integrations

- Implement `preview` as an optional orchestration layer over entry streaming and established external tools.
- Evaluate a TUI only for workflows that materially improve over `tree`, `find`, `read`, and shell composition.
- Evaluate read-only mount last. It requires measured demand, platform-specific dependency/licensing review, seek/caching semantics, and clear behavior for sequential or solid archives.
- Mutation through a mount is out of scope until transactional archive rewriting has a separate design.

Exit gate: each integration has an RFC, optional dependencies do not burden the default CLI, external-tool invocation is explicit and safe, and mount behavior never overstates random access.

## Cross-stage contracts

Every stage must preserve:

- explicit source locators and no ambiguous nested path grammar;
- stable structured errors and versioned schemas;
- bounded entry count, decoded bytes, nested depth, scan matches, and concurrency;
- truthful capability and access-cost reporting;
- stdout/stderr separation for stdio protocols and raw content streams;
- source preservation on error and verification before destructive commit;
- macOS/Linux tests, strict Clippy, release build, real integration smoke, and synchronized project documentation.

## Dependency order

```text
application service
  -> read-only MCP
      -> controlled MCP mutation
  -> HTTP remote source
      -> S3/SSH providers
  -> HTTP service
  -> FFI/language bindings

core entry streaming
  -> preview/TUI
  -> read-only mount evaluation
```

Stage 1 is complete in v0.5. Stages 2–6 remain planning boundaries and should not drive speculative abstractions into the core before their RFC and measurements exist.

## Standards baseline checked for this plan

- [Model Context Protocol official SDK status](https://github.com/modelcontextprotocol/modelcontextprotocol/blob/main/docs/docs/2026-07-28/sdk.mdx) and the [official Rust SDK roadmap](https://github.com/modelcontextprotocol/rust-sdk/blob/main/ROADMAP.md), checked 2026-08-28. The Rust SDK is Tier 2, so arcthis must pin and test a supported protocol revision rather than assume complete coverage of the newest revision.
- [MCP stdio transport](https://modelcontextprotocol.io/specification/2025-06-18/basic/transports) reserves stdout for protocol messages; logs belong on stderr.
- [MCP tool output](https://modelcontextprotocol.io/specification/2025-06-18/server/tools) can declare an output schema, and [resource reads](https://modelcontextprotocol.io/specification/2025-06-18/schema) can return text or blob content with a declared raw size.
- [RFC 9110 HTTP Semantics](https://www.rfc-editor.org/rfc/rfc9110.html#name-range-requests) makes byte-range support optional. Range caching must therefore validate partial-response semantics and representation validators instead of assuming every origin honors `Range`.
